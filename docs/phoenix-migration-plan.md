# PQ Companion → Elixir / Phoenix LiveView — Migration & Implementation Plan

**Created:** 2026-09-16
**Status:** plan only — no code written, no toolchain installed
**Scope of this document:** architecture assessment, target design, and a detailed
implementation plan for **Phase 0 (scaffolding)**, **Phase 1 (side nav)**, and
**Phase 2 (data model)** — plus a history-derived roadmap for the remaining waves.

**Decisions already taken (this session):**

| Decision | Choice |
|---|---|
| Desktop shell for overlays | **Deferred** — the plan keeps the shell behind a swappable adapter so the choice can be made later |
| Migration approach | **Clean-room rewrite** in Elixir; the Go/Electron app is reference-only, no dual-running |
| Deliverable | Plan document only |

Read `LIMITATIONS.md` alongside this document. Several of the *architectural* wins
listed in Parts II–III are direct fixes for limitations the current stack cannot
solve (notably §13.1, the broadcast-everything WebSocket hub).

### How this plan relates to OpenSpec

This document is the **architecture and roadmap**. The executable breakdown lives
in **`openspec/`** — one change per wave, each with a proposal, delta specs, a
design document and a verification-bearing task list.

## Part I — Assessment

### 1.1 What the app is today (measured)

| Surface | Size | Notes |
|---|---|---|
| Go backend | **89,100 LOC** production + 41,340 LOC tests | 61 internal packages |
| HTTP API | **333 routes**, 14,601 LOC of handlers | one file per resource |
| WebSocket events | **~30 distinct types** | single `Hub` broadcasts every event to every client |
| React frontend | **~99,200 LOC** ts/tsx | 62 pages, 58 hooks, 2 contexts |
| Electron shell | **4,165 LOC** | 16 transparent overlay windows, tray, auto-update |
| `quarm.db` (read-only) | 15 tables, ~85 MB | regenerated by the `data-release` workflow |
| `user.db` (read-write) | **50 tables**, + `config.yaml` (~186 fields) | migrations are inline DDL in Go stores |
| Test suite | 1,249 Go test funcs / 187 files; 20 Playwright specs | |

Git history: **1,725 commits** — 769 `feat`, 640 `fix`, 114 `docs`, 104 `chore`,
24 `perf`, 23 `refactor`. Monthly cadence peaked at ~500 commits/month
(2026-06) and settled to ~85/month (2026-09) in the maintenance phase.

### 1.2 The five hard constraints

Every architecture decision below is downstream of these. None are negotiable.

1. **Windows-local, same machine as the game.** Zeal exports files into the EQ
   directory; the log lives there; ZealPipes is a **Windows named pipe**. The
   Elixir node runs on the player's Windows box. This is not a hosted web app.
2. **Transparent, always-on-top, click-through windows over a DirectX game.**
   A browser cannot do this. LiveView can *render* an overlay; only a native
   shell can make it float. Hence the adapter.
3. **Windows named pipes** (`\\.\pipe\...`). The BEAM has no first-class
   named-pipe support — see §2.5.
4. **Local file integration.** Log tailing, reading/writing `.ini` files,
   `spells_en.txt` overrides, Brewall map packs, Zeal XML/INI exports, and
   map annotations written back to the in-game `/map`.
5. **SQLite for everything.** `quarm.db` is read-only and shipped;
   `user.db` is read-write and holds real user data that must survive adoption.

### 1.3 What LiveView buys

- **333 REST routes and ~30 WS event types collapse.** No API client, no
  `services/api.ts` (3,387 LOC), no `useWebSocket` singleton, no manual
  refetch-on-event. Server state is the UI state.
- **PubSub replaces broadcast-everything.** Each overlay subscribes only to its
  own topic, which structurally fixes LIMITATIONS §13.1 (Chat History re-fetches
  the entire feed on every live update) and removes the current hub's
  drop-slow-client behaviour.
- **Changesets replace hand-rolled validation** across 50 tables and the
  186-field config.
- **One language** for the whole stack. The Go↔TS type duplication
  (`types/` mirroring Go structs, `npcHelpers.ts` mirroring
  `special_abilities.go`) disappears.
- **LiveView streams** fix the unbounded-list problem in Log Feed, Combat
  History, Chat History, Loot Tracker and Player Tracker.
- Deploy/packaging story is a **single `mix release`** instead of a
  Go cross-compile + electron-vite build + electron-builder chain, plus a
  documented electron-builder bug that mangles `package.json` on every build.

### 1.4 What it costs

- **Every line is rewritten.** 130k LOC of Go (including 41k of tests that
  encode real EQ log formats) and 99k LOC of React.
- **Windows is a second-class OTP platform.** `mix release` works, but NIF
  precompilation, `:peer`, fork-based features, and some libraries assume
  Unix. `exqlite` ships Windows x64 precompiled NIFs; other candidates must be
  vetted individually.
- **Named pipes need a bridge** (§2.5), which is the single largest technical
  unknown.
- **Two features need JS hooks regardless** of the migration: the two
  graph pages (`@xyflow/react` + `dagre` — Schema Graph, PoP Flags) and
  drag-reorder (sidebar favorites, trigger categories, wishlist slots).
- **Fidelity risk on regex.** Go uses RE2; Elixir uses PCRE. Community trigger
  packs were authored against GINA-style patterns; PCRE is *more* permissive so
  patterns should port, but capture-group and token semantics (`{c}`,
  `{target}`) need explicit parity tests.

### 1.5 Verdict

The migration is **justified but not urgent**, and it is a **multi-quarter
rewrite**, not a refactor. The strongest arguments are structural: the
broadcast-everything hub, the duplicated type layer, and the 333-route REST
surface are all debt that LiveView deletes rather than repays. The strongest
counter-argument is the overlay/named-pipe surface, which is genuinely hostile
to a web framework.

The plan therefore front-loads the parts that are **shell-independent and
low-risk** (scaffolding, nav, data model, read-only game DB) so value lands
before the shell decision is forced.

### 2.2 App structure — bounded contexts

Recommend **one OTP app with bounded contexts** (not an umbrella). The current
codebase's 61 packages map cleanly onto ~12 contexts, and a single app keeps
`mix release` simple. An umbrella is defensible for compile-time boundary
enforcement; treat it as an open decision (§8) — but the module layout below is
identical either way.

```
PQ.Game          # quarm.db reads: Item, Spell, NpcType, Zone, Recipe, Quest
PQ.Character     # characters, AAs, skills, tradeskills, wishlist, upgrades
PQ.Log           # tailer, parser, event pipeline  ← the spine
PQ.Combat        # fights, DPS/HPS, history
PQ.Threat        # hate estimation, raid threat
PQ.SpellTimer    # timer engine, buff/detrimental overlays
PQ.Trigger       # regex engine, packs, categories, alert actions
PQ.Timer         # custom timers, timer groups
PQ.Zeal          # file watcher + pipe bridge client + protocol decode
PQ.Overlay       # window specs, positions, lock/zoom/HUD mode
PQ.Maps          # map parsing, annotations, live position
PQ.Raid          # composition, encounters, readiness, roster
PQ.Config        # config.yaml as changesets + ConfigServer
PQ.Audio         # TTS (piper/kokoro as Ports), sound assets
PQ.Shell         # the swappable native-shell adapter  ← §2.4
```

> **Namespace convention.** The `PQ.*` names below are **shorthand**. The
> generated app's real namespaces are **`PQCompanion.*`** and
> **`PQCompanionWeb.*`** (e.g. `PQCompanion.Config`, `PQCompanionWeb.Nav`). Code
> and every OpenSpec change artifact use the real names; this plan keeps the
> short alias for readability. Never let both spellings appear in code.

The **critical dependency** is `PQ.Log`. Nothing in the parsing/overlay/tracker
half of the app works without it, so it lands first (Wave 1).

| `combat:update` | `overlay:combat` | DPS overlay, Combat Log |
| `npc:target` | `overlay:npc_target` | NPC Info overlay |
| `timers:buff`, `timers:detrim` | `overlay:timers` | Buff/Detrim timer overlays |
| `timers:custom` | `overlay:timers` | Custom Timer windows |
| `triggers:fired` | `trigger:fired`, `trigger:test*` | Trigger overlay, Triggers page |
| `respawns:update` | `overlay:respawns` | Respawn overlay |
| `rolls:update` | `overlay:rolls` | Roll overlay, Roll Tracker |
| `threat:update`, `raidthreat:update` | `overlay:threat`, `overlay:raidthreat` | Threat overlays |
| `factions:update` | `overlay:factions` | Factions page |
| `chat:new` | `chat:new` | Chat History (topic-scoped) |
| `loot:new` | `loot:new` | Loot Tracker |
| `players:update` | `player:group_positions`, `player:position` | Live Map, Players |
| `character:zone` | `character:zone` | Active-character consumers |
| `zeal:state` | `zeal:connected/disconnected/quarmy`, `zeal:inventory`, `zeal:spellbook`, `zeal:bandolier`, `zeal:macros`, `zeal:spellsets` | Character pages |

`PQ.Shell` is **not** a PubSub listener — it is a layout-level concern (§2.4).

### 2.4 The shell as a swappable adapter

The LiveView server is authoritative about *what* a window is. The shell is
authoritative about *how* to realise it. The contract travels in the page.

```elixir
defmodule PQ.Shell do
  @type window :: %{
          id: String.t(),           # "npc-overlay", "dps-overlay", ...
          token: String.t(),        # LiveView session token for the window route
          route: String.t(),        # "/w/npc-overlay"
          title: String.t(),
          transparent: boolean(),
          always_on_top: boolean(),
          click_through: boolean(),
          frameless: boolean(),
          resizable: boolean(),
          display_only: boolean(),  # HUD mode: ignore mouse, no chrome
          bounds: %{x: integer(), y: integer(), w: integer(), h: integer()} | nil,
          zoom: float()
        }

  @callback open(PQ.Shell.window()) :: {:ok, term()} | {:error, term()}
  @callback close(String.t()) :: :ok | {:error, term()}
  @callback resize(String.t(), map()) :: :ok
  @callback set_click_through(String.t(), boolean()) :: :ok
  @callback focus(String.t()) :: :ok
  @callback list() :: [PQ.Shell.window()]
end
```

**Delivery mechanism.** The overlay layout renders a single machine-readable
tag:

```heex
<meta name="pq-window" content={Jason.encode!(@window_spec)} />
```

The shell's preload script scrapes it on load and forwards it to the main
process, which configures the native window. Live updates (lock, zoom,
display-only, moved bounds) go out as `push_event("pq:window", patch)` — the
same event bus the renderer already has open. Bounds persistence comes back as
`pushEventTo`/`handleEvent("pq:save_bounds")` from a small drag/resize hook.

Adapters:

| Adapter | Status |
|---|---|
| `PQ.Shell.Browser` | **dev default** — opens a normal tab; ignores transparency. Ships in Phase 0 so the whole main window works with zero native code. |
| `PQ.Shell.Electron` | candidate — reuses today's 4.2k-LOC window manager almost verbatim, ported to scrape `pq-window` |
| `PQ.Shell.Tauri` | candidate — smaller binary, but the window manager is a rewrite |

Because `PQ.Shell.Browser` exists from Phase 0, **no wave is blocked on the
shell decision** except Wave 6 (overlays) — which is last-but-two anyway.

### 2.5 Windows named pipes — the one real technical unknown

The BEAM cannot open `\\.\pipe\<name>` reliably through `:file`. Three options:

| Option | Assessment |
|---|---|
| **A. Small native pipe-bridge sidecar** | Recommended. A ~300-LOC Rust or Go binary reads the Zeal pipes, frames JSON lines on stdout, and the BEAM consumes it via `Port`. Keeps all native risk out of the BEAM, is trivially testable, and survives OTP upgrades. The existing `zealpipe` decoder (870 LOC) is the reference for the wire format. |
| **B. NIF via `:erlang.open_port` on a helper** | Same as A with less process isolation. Not worth it over A. |
| **C. Zig/Rustler NIF doing the named-pipe read inline** | Fastest path on paper, but couples the app to NIF ABI, complicates `mix release` on Windows, and a NIF crash takes the node down — unacceptable for a gaming companion app. |

**Recommendation: A.** Validate it in Wave 1 with a spike before committing to
Wave 6. Note that the `zealpipe` wire format was itself reverse-engineered and
mis-decoded once (see handoff.md: "Zeal's raid wire format never matched our
decoder"), so port the *existing* decoder's tests as the contract.

### 3.4 Configuration and paths

Mirror the Go app's filesystem contract exactly so existing installs keep
working:

| Artifact | Path | Access |
|---|---|---|
| App home | `~/.pq-companion/` | — |
| `config.yaml` | `~/.pq-companion/config.yaml` | read-write, YAML, **format unchanged** |
| `user.db` | `~/.pq-companion/user.db` | read-write |
| `backups/` | `~/.pq-companion/backups/` | read-write |
| `quarm.db` | `backend/data/quarm.db` → `phoenix/priv/data/quarm.db` | **read-only** |
| `maps.db` | shipped next to the release | **read-only** |
| server log | `~/.pq-companion/logs/server.log` | append |

Two repos in `config/config.exs`:

```elixir
config :pq_companion, PQ.UserRepo,
  database: Path.expand("~/.pq-companion/user.db"),
  journal_mode: :wal, busy_timeout: 5_000, pool_size: 5

config :pq_companion, PQ.QuarmRepo,
  database: Path.expand("priv/data/quarm.db"),
  read_only: true, pool_size: 5
```

`PQ.QuarmRepo` must be **structurally incapable** of writes. Enforce with
`read_only: true` *and* a `PQ.QuarmRepo` wrapper that rejects anything but
`all/2` and `one/2` in dev, plus a test that asserts `INSERT` raises.

**Port announcement.** The shell needs to discover the port (the Go backend
already does OS-assigned fallback for port resilience). Keep that contract:
write `~/.pq-companion/runtime.json` (`{"port":..., "pid":..., "version":...}`)
at boot *and* print a single machine-readable line on stdout, exactly as the
sidecar does today.

### 3.5 Layouts

Three layouts, matching the current app's three window classes:

| Layout | Routes | Contract |
|---|---|---|
| `:root` | main window | sidebar + titlebar + content |
| `:overlay` | 16 overlay routes | transparent body, no chrome, emits `pq-window` meta |
| `:bare` | onboarding wizard, modals | no sidebar |

`document.body.style.backgroundColor = 'transparent'` in the React
`OverlayPage` wrapper becomes a CSS class on `<body>` in the `:overlay` layout —
which removes the whole class of bugs around reverting the transparent body
(the "overlay turned into a black box" regression documented in `App.tsx`).

The overlay layout must **not** run audio/alert hooks. Today that is enforced by
rendering a different React tree (`MainWindowLayout` vs `OverlayPage`); in
LiveView it is enforced by the layout + a `PQ.Shell.overlay?/1` guard.

### 3.6 Dev workflow

```bash
cd phoenix
mix deps.get && mix ecto.setup   # or mix pq.db.adopt for an existing install
mix phx.server                   # http://localhost:4000
```

`PQ.Shell.Browser` is the default in dev, so the main window and all 16 overlay
routes are reachable as ordinary URLs. Live reload works normally — no Electron

### 3.7 CI

Extend `.github/workflows/ci.yml` with a parallel Elixir job:

- `erlef/setup-beam` pinned to `.tool-versions`
- download `quarm.db` from the `data-latest` release (same step the Go job uses;
  `PQ.QuarmRepo`-backed tests skip when absent)
- `mix deps.get`, `mix ecto.create`, `mix test`, `mix format --check-formatted`
- `mix credo --strict` and `mix dialyzer` as non-blocking initially, then

- `mix sobelow` once the shell/HTTP surface exists

Keep the Go and TS jobs **during** the migration so the reference app stays

### 3.8 Phase 0 acceptance criteria

1. `mix phx.server` boots, serves `/`, and connects a LiveView over WebSocket.
2. `PQ.UserRepo` opens the **existing** `~/.pq-companion/user.db` and can read
   and write a row without schema change.
3. `PQ.QuarmRepo` reads `items`, `spells_new`, `npc_types`, `zone` and rejects a
   write.
4. `~/.pq-companion/config.yaml` is **left untouched** by boot — Wave 0 only
   resolves its location. The full round-trip (load → change → atomic save →

   deliverable of `add-data-model`, where the settings schema lives.
5. The three layouts render; `/w/npc-overlay` renders a transparent route with
   the `pq-window` meta tag present and parseable.
6. CI is green on the Elixir job.

## Part IV — Phase 1: Side Nav

The highest-value early win: small, self-contained, and it validates the
layout/component/live-navigation model before any domain porting.

### 4.1 Port the canonical definition

`frontend/src/lib/sidebarNav.tsx` is already the single source of truth shared
by the live sidebar and the Settings → Navigation editor. Preserve that
property — it is the reason the two surfaces never drift today.

```
lib/pq_web/nav.ex
  defmodule PQWeb.Nav
    defmodule Item, do: defstruct [:to, :label, :icon, :flag, :end, :section]
    @sections [ ... compile-time data, 4 sections, 34 items ... ]
    def sections/0
    def visible/1        # flags -> sections        (visibleNavSections)
    def favorites/3      # sections, favorites, order -> items  (favoriteItems)
    def order/2          # items, order -> items     (orderItems)
end
```

**Parity checklist — port verbatim, then diff against the TS:**

- 4 sections: `database` (9), `characters` (15), `raids` (1), `parsing` (9).
- 3 flag-gated items: `/pop-flags` → `pop_flags_enabled`,
  `/characters/factions` → `faction_tracker_enabled`,
  `/raids` → `raids_enabled`.
- Sections with **zero** visible items disappear entirely
  (`visibleNavSections` drops empty sections — this is why Raids is invisible
  by default).
- `end: true` on `/raids` only. Exact-match highlighting is required because
  `/raids` is a parent of `/raids/editor`. **Do not** default `end` to true —
  `/combat` relies on prefix matching to stay lit across `/combat/log` and
  `/combat/history`, which are not separate sidebar rows.
- `orderItems/2` keeps unlisted items **after** listed ones in their original
  relative order (`Number.MAX_SAFE_INTEGER` sentinel → a `nil`-safe sort key).
- Favorite items are resolved from the *flag-filtered* section list, so a
  hidden dev-gated tab can never appear in Favorites.

### 4.2 Live navigation model

Use **one LiveView per route** with a shared layout, plus **sticky**
`live_render` for the surfaces that must not remount:

```heex
<%# layouts/app.html.heex %>
<.sidebar sections={@nav_sections} active={@active_path} />
<%= live_render(@socket, PQWeb.SidebarControlsLive, id: "sidebar-controls", sticky: true) %>
<%= @inner_content %>
```

Sticky children:
- **Character switcher** — currently receives `config:character_detected` and
  `config:updated`; must survive navigation without refetching.
- **Log-status indicator** — currently polls `getLogStatus()` on a timer; the
  poll moves into the sticky LiveView.
- **Back/forward history** (`useHistoryNav`) — replaced by LiveView's own
  navigation history; the sticky control renders browser-style nav.

Active-path highlighting: an `on_mount`/`attach_hook(:active_path, :handle_params, ...)`
hook writes `@active_path` into the socket, and `Nav.Item.end?` decides
exact-vs-prefix matching. This replaces react-router's `NavLink` semantics.

**Do not** try to preserve React's `HashRouter`. Overlay windows are separate
native windows hitting separate URLs, so plain path routing is correct here, and
it removes the deep-link indirection (`window.electron.app.onNavigate`).

### 4.3 Icons

Today: `lucide-react`, 32 named icons in `sidebarNav.tsx`. Options:

| Option | Verdict |
|---|---|
| `heroicons` hex package | Fastest, but icon shapes differ from Lucide → visual drift |
| Vendor Lucide SVG paths into `PQWeb.Icons` | **Recommended** — a small HEEx function component per icon, verbatim paths, zero drift, no JS |
| Lucide via a JS hook | Rejected — reintroduces a JS build dep for static art |

Vendor the paths. The mapping is `to → icon` and it must stay 1:1 so the nav
looks identical, which matters because the Nav is what users stare at all day.

### 4.4 Preferences (hide / order / favorites / collapsed)

Today this is split:

| State | Today | Target |
|---|---|---|
| Hidden tabs, order, favorites | **backend `config.yaml` preferences** via `useSidebarPrefs` | `PQ.Config` fields (unchanged key names) — survives as-is |
| Section collapse | `localStorage['sidebar_collapsed_sections']` | **Move to `PQ.Config`** — it is genuine user state that should survive a reinstall, and localStorage is a per-window/per-origin accident in a multi-window app |
| Settings → Navigation editor | shares `NAV_SECTIONS` | shares `PQWeb.Nav` |

Favorites drag-to-reorder: phase 1 ships **move-up / move-down buttons**
(server-side `handle_event`, no JS). Add a `phx-hook` sortable in a later polish
pass — the same hook will later serve trigger categories and wishlist slots.

### 4.5 Phase 1 acceptance criteria

1. All 34 nav items render, in the same 4 sections and order, from
   `PQCompanionWeb.Nav`.
2. Toggling each of the 3 flags off removes its item; emptying a section
   removes the section.
3. Navigating `/combat/log` → `/combat/history` keeps Combat Log lit;
   `/raids/editor` does **not** keep `/raids` lit.
4. Hide / order / favorites / collapse all persist across a restart.

### 5.2 Game data schemas (quarm.db)

Straightforward Ecto schemas with `@primary_key` overrides — most of these

### 5.3 User data schemas (user.db)

Full inventory in **Appendix A**. Three patterns cover all 50 tables:

- **Per-character child tables** (`character_aas`, `character_tradeskills`,
  `character_raid_buffs`, `character_skills`, …) — `belongs_to :character`.
  Note that `characters` has an integer `id` **and** a unique `name`
  (the name is the real-world key, since Zeal identifies characters by name).
  Preserve that: several tables key on `character` **name** as a string
  (`keyring_entries`, `lockout_entries`, `loot_events`,
  `character_progress_events`, `pop_flag_state`) rather than the id. Do not
  "normalise" this during the port — it is load-bearing for how the log parser
  identifies the active character.
- **Global single-row-ish state** (`player_sightings`, `player_notes`,
  `player_interactions`, `map_annotations`, `saved_queries`,
  `trader_snapshots`, `combat_fights`, `loot_events`).
- **JSON-blob columns.** Several tables store serialized structures in TEXT:
  `triggers.actions`, `triggers.timer_alerts`, `triggers.characters`,
  `combat_fights.combatants_json`, `character_upgrade_weights.weights_json`,
  `mystats.character_stat_snapshots.parsed_json`, `raid_roles.class_codes`.
  Map these to `Ecto.Type` embedded schemas (`PQ.Trigger.Action`,
  `PQ.Combat.Combatant`, `PQ.Character.UpgradeWeights`, …) so validation
  happens at the boundary instead of in ad-hoc unmarshal code. **The on-disk
  JSON shape must not change** — it is embedded in user data and in
  export/import bundles.

### 5.4 Adoption strategy for an existing `user.db`

This is the highest-risk part of Phase 2. Real user data exists and must
survive.

The Go app's migrations are inline `CREATE TABLE IF NOT EXISTS ...` DDL inside
each store, plus ad-hoc `ALTER TABLE` upgrades. There is **no** migration
version table.

**Recommended approach:**

1. **Reverse-engineer Ecto migrations** from the Go DDL, one migration per
   domain, using `CREATE TABLE IF NOT EXISTS` semantics so both a fresh install
   and an adopted install converge.
2. Accept that Ecto adds a `schema_migrations` table to `user.db`. Harmless,
   and it gives the Elixir app what the Go app never had.
3. Ship `mix pq.db.adopt` — a task that:
   - snapshots `user.db` to `user.db.pre-migration` **before** touching it,
   - compares every Elixir schema's `__schema__(:fields)` against
     `PRAGMA table_info(<table>)`,
   - **fails loudly** on unknown/drifted columns rather than silently ignoring
     them (a silently-ignored column is how data loss happens),
   - reports tables present in SQLite but absent from the schemas — this is how
     the orphaned tables from the converter/sandbox experiments
     (`above`, `result`, `statement`, `used`) and any future stray get caught.
4. Add a round-trip test: take a fixture `user.db` captured from a real install,
   run `mix pq.db.adopt` + the full app read path, and assert no field loss.
5. The app-state export/import (`PQ.Backup`) must keep producing bundles the
   **Go app can still read**, for the duration of the migration, so a user can
   roll back. Freeze that format and test it in both directions until the
   reference tree is deleted.

### 5.5 Config as changesets

`backend/internal/config/config.go` is 1,494 LOC and ~186 fields across
`Config`, `BackupSettings`, `SpellTimerSettings`, `DPSClassColors`,
`CombatSettings`, `Preferences`, `DiscordVoiceLink`, `DiscordWebhook`,
`WishlistWatchSettings`, `TimerAlertPref`, `OverlayPosition`,
`NPCOverlaySections`, `CHChainSettings`.

Target:

```elixir
defmodule PQ.Config.Schema do
  use Ecto.Schema
  import Ecto.Changeset
  @primary_key false
  embedded_schema do
    embeds_one :backup, PQ.Config.Backup
    embeds_one :spell_timer, PQ.Config.SpellTimer
    embeds_one :combat, PQ.Config.Combat
    embeds_one :preferences, PQ.Config.Preferences   # the big one
    ...
  end
end
```

Rules:

- **`config.yaml` key names are frozen.** They are user data.
- Keep the Go app's defaults byte-for-byte; port `config_test.go` (482 LOC) as
  the defaults contract.
- One writer: `PQ.Config.Server` (a `GenServer`) owns the struct in an ETS/
  `:persistent_term` cache, serialises writes, and performs the
  **write-temp-then-rename** atomic save the Go version already does. This
  replaces the `cfgMgr` mutex and the documented atomic-save hardening.
- On successful save, broadcast `config:updated` — every LiveView subscribes
  (via a shared `on_mount`) so a Settings change is reflected app-wide without
  a reload. This is exactly what the current app does with the `config:updated`
  WS event, so behavior is preserved.
- A second file watcher covers external edits, matching today's behaviour.

### 5.6 Phase 2 acceptance criteria

1. Every one of the 50 user.db tables and 15 quarm.db tables has an Ecto schema
   whose fields exactly match `PRAGMA table_info` (enforced by a test).
2. `mix pq.db.adopt` runs against a real captured `user.db`, produces a backup,
   and reports zero drift.
3. A write round-trips: change a setting → reload → same value; change a
   character row → reload → same value.
4. `PQ.QuarmRepo` rejects writes.
5. Config round-trips through YAML with key names unchanged, and differs from
   Go output only in fields the user actually changed.
6. App-state export from the Elixir app is readable by the **Go** app (parity
   fixture test).
7. Pure-function ports (`SpellFormula`, `SpecialAbilities`, `Haste`,
   `Variants`, `Resist`, `Charm`, `Upgrade`) pass the ported Go table-driven
   test cases.

## Part VI — Feature Roadmap

### 6.1 Ordering principles derived from the git history

The history shows the app was built as:
**database explorer → Zeal/file integration → log parsing & overlays →
combat/DPS → triggers & audio → character tools → trackers → maps → raids.**

Three observations drive the migration order:

1. **The log pipeline is the spine.** `feat(logparser)` and `feat(zealpipe)`
   commits appear before every tracker, overlay and trigger feature. Nothing in
   the second half of the feature list works without it.
2. **Read-only game data is the lowest-risk, highest-volume win.** The Database
   section is 9 of 34 nav items and depends only on `quarm.db` — no files, no
   pipes, no shell.
3. **Triggers are the largest single feature by churn** (~176 commits, 9,852 LOC
   production) and they depend on both the log pipeline and audio, so they land
   late despite their size — porting them early would stall on two unported
   dependencies.

### 6.4 Test strategy for a clean-room port

There is no incremental safety net, so the safety net must be the tests.

1. **Port the log-format fixtures first, verbatim.** `logparser`'s tests (2,393
   LOC) encode real EQ log lines across every combat/spell/zone/tell variant.
   They are the single most valuable asset in the Go tree — they are a
   machine-checkable spec for the highest-risk subsystem. Port them as
   `PQ.Log.ParserTest` before writing the parser.
2. **Same for `zealpipe`** (446 LOC of tests): the wire format was
   mis-decoded once already.
3. **Same for the pure game-math functions** (§5.2) and the config defaults.
4. **Skip** the handler-level Go tests (`api/*_test.go`) — those assert on an
   HTTP surface that ceases to exist. Replace with LiveView tests
   (`Phoenix.LiveViewTest`) asserting rendered output.
5. **Keep Playwright** for end-to-end smoke against the LiveView app. The
   existing `e2e/smoke/app-smoke.spec.ts` assertions (shell render, nav, overlay
   states) translate directly, and the `api` project is dropped.
6. **Add a golden-file parity harness** during Waves 4–6: run the same query
   against the Go backend and the LiveView app and diff the rendered result for
   a fixed set of inputs. This is the only mechanical check that a port is
   faithful, and it should be temporary scaffolding.

## Part IX — Duplicated logic: collapse, keep, or delete

### 9.1 What is actually duplicated

The reference duplicates logic in three distinct ways, and they have different
correct answers.

| Kind | Measured today | Verdict |
|---|---|---|
| Go↔TS behavior mirrors | `npcHelpers.ts` (175 LOC) mirrors `db/special_abilities.go` + `db/enums/special_abilities.go`. `claude.md` documents the mirror. | **Collapse** |
| Hand-written type mirrors | `frontend/src/types/` — 3,922 LOC across 35 files mirroring Go structs | **Delete, no replacement** |
| Code→label maps | **31 files** containing `map[int]string` in Go, plus 12 TS label modules | **Triage** (see 9.3) |
| Runtime cache of the catalog | `enumsCache.ts` (177 LOC) | **Delete** |

Two corrections to widely-held assumptions, both verified:

- **`enumsCache.ts` is not a second definition.** It is a cache hydrated from the
  backend at boot (`loadEnums()`). It matters for a different reason: on fetch
  failure the reference proceeds anyway and helpers silently render stub labels
  like `"Tradeskill 75"`. Server-rendered lookup makes that failure mode
  impossible, so the cache is deleted rather than ported.
- **The enum catalog's real duplication is special abilities in three places**
  (Go parsing, Go labels, TS both) — not the cache.

### 9.2 Why nothing caught this: there is no parity guard

`grep -E 'enum|parity|audit|generat' .github/workflows/ci.yml` returns **nothing**.
The only guard that exists, `internal/db/enums/audit_test.go` + `cmd/enum-audit`,
checks *coverage against the database* — every observed code has a label — not
Go↔TS agreement.

The cost is documented in `enum-audit.md`: spell `targettype=4` was labelled
"Single (Pet)" when it should have been "PB AE", affecting **325 spells**. It was
found by a human reading a generated sample report against pqdi.cc, not by a test.
A rewrite that consolidates once but adds no guard will re-acquire this bug.

### 9.3 The four buckets

Triage every apparent duplication into exactly one:

1. **Delete with no replacement.** Anything existing only because of the Go↔TS
   boundary: the `types/` tree, `enumsCache.ts`. LiveView renders server-side, so
   there is no client/server seam to mirror across.
2. **Collapse to one definition.** Same-fact duplicates: special abilities, and
   the game-data members of the 31 `map[int]string` files. These get one module
   and one guard test.
3. **Keep as data, single-owner.** The hand-maintained JSON catalogs
   (`aa_descriptions.json`, `pop_gated.json`, `quest_sources.json`,
   `tradeskill_paths.json`, `popflag/flags.json`) load from one place and are
   validated by a well-formedness test — plus the ported `enum-audit`
   coverage check against the real database.
4. **Keep separate — do NOT merge.** Presentation and client-only concerns that
   merely *look* like duplicates: `combatantColor.ts`, `chChainPatterns.ts`,
   `overlayTextStyle.ts`, `dpsClipboard.ts`. Merging these is over-consolidation
   and would push presentation decisions into the data layer.

### 9.4 The anti-drift rule

Consolidating once is not enough — re-divergence must be structurally hard:

> If a remaining JavaScript hook (the xyflow graph pages, drag-reorder) needs
> labels or codes, the server renders them into the page payload. **The hook
> never carries its own copy.**

This is the only surviving client-side code, so it is the only place duplication
could creep back. A guard test asserts no second definition of a collapsed
catalog exists, and is proven to fail when one is introduced.

### 9.5 Deleting reference code — delete-as-you-go

**Delete a reference package in the same change that lands its port**, once that
port's tests are green. Do not hold the whole Go tree until Wave 11.

Why, given the plan already says Wave 11 deletes the trees:

- **Nothing is ever lost.** The Go app lives permanently on `upstream/main`. Any
  deleted file is one `git show upstream/main:backend/internal/<pkg>/<file>` away.
  This is what makes deletion from the working tree free — and it is a direct
  consequence of the migration being a permanent fork divergence rather than an
  upstream contribution.
- **Dead code is how you edit the wrong tree.** Every wave's tasks currently end
  by asserting `git diff --stat` against the reference trees is empty. That guard
  is only *meaningful* while the ported code is present; once a package is
  deleted, the guarantee is structural instead of asserted.
- **It makes each wave's diff legible.** "This wave removed `internal/logparser`
  and added `PQ.Log`" is reviewable. A 89,000-LOC deletion in Wave 11 is not.
- **It prevents a shadow dependency.** A buildable Go app in-tree invites "just
  run the old one to check" — which quietly makes the migration's correctness a
  two-toolchain problem, and makes the frozen-reference rule unenforceable in
  practice.

An honest caveat: deleting the reference removes the ability to diff against real
behavior. That is exactly why Waves 3–6 (the spine, the game database, the
parsing section) must record **one golden-file parity pass** — the same input
through the Go app and the Elixir app, diffed — before each port's reference is
deleted. After Wave 6 the remaining surfaces are UI-dominant, where the ported
tests and the specs carry the contract.

Wave 11 therefore becomes: delete what is *left* (`electron/`, `frontend/`, and
unported `backend/` packages), plus the release scripts and guards that only
existed for the reference.
