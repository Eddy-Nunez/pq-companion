## 3. Shell adapter contract

- [x] 3.1 Define the `PQ.Shell` behaviour with the window struct and the open/close/resize/set_click_through/focus/list callbacks; verify the behaviour compiles and feature code references only the behaviour (design D3) — **verified 2026-09-18.** The module is `PQCompanion.Shell`: the plan and these specs write the short `PQ.*`/`PQWeb.*` aliases, but the generated app's namespace is `PQCompanion` and every existing module (`PQCompanion.Windows`, `PQCompanion.Audio`, `PQCompanion.Repo`) uses it — renaming the tree for the alias would be churn with no behavioural gain, and the overlay shell already pointed at `PQCompanion.Shell`. `@type window/0` carries id, slug, kind, token, route, title, transparent, always_on_top, click_through, frameless, resizable, display_only, bounds and zoom; the six `@callback`s match plan §2.4. `Shell.spec/1` builds a spec from the static `Windows` declaration plus runtime overrides from the new `PQCompanion.WindowState`, and signs a per-window session token (`Phoenix.Token.sign`, salt `pq-window`); `Shell.to_json/1` maps the spec to the shell's camelCase keys. Every operation dispatches through `Shell.adapter/0`, which reads `config :pq_companion, :shell_adapter` (default `PQCompanion.Shell.Browser`). **Verified:** a test asserts `Shell.behaviour_info(:callbacks)` lists all six operations; a source test asserts no module under `lib/pq_companion_web/` names `Shell.Browser`; a config-swap test puts `IncompleteAdapter` into `:shell_adapter` and asserts `Shell.adapter/0` returns it and `Shell.open/1` dispatches to it. `mix compile --warnings-as-errors` clean.
- [x] 3.2 Render the `pq-window` meta tag from the overlay layout and a main-window spec from the root layout; verify a test parses the tag as JSON and asserts every required key is present on both window classes — **verified 2026-09-18.** Both `overlay.html.heex` and `root.html.heex` render `<meta name="pq-window" content={Shell.to_json(Shell.spec(window))}>`; the root tag is guarded with `:if={assigns[:window]}` because the root layout is also the document for any future non-window route. **The two keys the old `meta_payload/1` could not carry are resolved:** the session `token` rides in the spec (signed per call) and `bounds`/`zoom`/`display_only`/`click_through` come from `PQCompanion.WindowState`, so both live in `Shell.spec/1` rather than in `PQCompanion.Windows` — the registry stays a pure static declaration, and `Windows.meta_payload/1` (the old string-keyed builder) was deleted rather than duplicated. **Verified:** tests parse the tag with `LazyHTML` (not a regex — HEEx HTML-escapes the attribute and `&quot;` breaks Jason; parsing is also what a shell does) and assert `id, slug, kind, token, route, title, transparent, alwaysOnTop, clickThrough, frameless, resizable, displayOnly, bounds, zoom` are present on **both** classes, that the overlay is transparent/non-resizable and the main window non-transparent/resizable, and that the token verifies via `Shell.verify_token/2`. - [x] 3.3 Implement `PQ.Shell.Browser` as the development default, recording received specs and reporting native-only properties as unmet rather than succeeding; verify a test asserts transparency is reported unmet — **verified 2026-09-18.** `PQCompanion.Shell.Browser` is a `GenServer` in the supervision tree and the configured default. `open/1` records the spec and returns `{:ok, %{id:, route:, unmet:}}`, where `unmet` lists every native-only property the spec asked for (`:transparent`, `:always_on_top`, `:click_through`, `:frameless`, `:display_only`, plus `:bounds` when one is requested) — a browser tab can honour none of them, so the adapter reports rather than claiming success. `resize/2` and `set_click_through/2` record the change and return their `:unmet` list; `focus/1` marks the entry; `close/1` removes it; `list/0` returns the recorded specs. **Verified:** tests assert `:transparent`, `:always_on_top` and `:frameless` are all in `unmet` for an overlay, `:click_through` is in `unmet` for `set_click_through/2`, and a main-window spec (no native-only property) yields `unmet: []`. - [x] 3.4 Implement the adapter conformance suite and run it against `PQ.Shell.Browser`; verify it passes, and verify it fails with a named missing operation when run against a deliberately incomplete stub adapter — **verified 2026-09-18.** `PQCompanion.Shell.Conformance.run/1` checks the six operations are exported (`function_exported?/3`, after `Code.ensure_loaded/1`), then exercises each, accepting `:ok`/`{:ok, _}`/`{:error, _}` for mutations and a list for `list/0`, and collects contract violations and raised exceptions as `{:error, reasons}` with one reasoned string per operation — so a failure *names* the operation. - [x] 3.5 Implement `push_event`/`handleEvent` propagation for bounds, zoom, display-only, click-through and lock; verify a test asserts a display-only toggle reaches the shell as an update with no reload, and that reported bounds are persisted and re-applied on next open — **verified 2026-09-18.** `PQCompanionWeb.ShellEvents` holds one handler for all five properties, delegated to by `WindowLive` and `OverlayLive` `handle_event("pq:" <> _, ...)` clauses, so the two window classes cannot drift. Outbound, `Shell.spec/1` reads `WindowState`, so the next `open/1` carries the stored bounds; the server-side `push_event` is an incremental socket diff, never a navigation. A `PqWindow` hook in `assets/js/app.js` reports debounced browser bounds back and a `phx:pq:window` listener forwards pushed patches to `window.pqShell` when a native shell injects it (absent in a browser — a deliberate no-op). **Verified:** `render_hook` a display-only toggle → `assert_push_event` `%{id: "npc", patch: %{display_only: true}}`, `WindowState` updated, and `render/1` still shows the same overlay (no redirect/reload); zoom, click-through and lock propagate too, on the main window as well; a seeded `pq:save_bounds` is asserted in `WindowState` **and** in the spec handed to `Browser.open/1`. Suite: 53 tests, 0 failures; `mix assets.build` succeeds.
